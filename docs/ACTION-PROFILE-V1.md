# 兼容动作档案 v1（Compatibility Action Profile v1）

**状态：冻结（2026-08）** · Schema：[`profiles/schema/action-profile-v1.schema.json`](../profiles/schema/action-profile-v1.schema.json)

一份兼容动作档案描述：**如何从外部可靠地执行第三方软件里的一个业务动作，并证明它成功了。**

本文档中的"必须 / 不得 / 应当 / 可以"按 RFC 2119 理解。

---

## 0. 这个格式想解决的问题

今天的 GUI Agent 靠截图猜按钮。真正卡住它们的不是"点不准"——是**点完之后没人知道点对了没有**。
所以 v1 的重心不在"怎么点"，在另外三件事：

| 关切 | v1 的回答 |
|---|---|
| 这是哪一个业务动作？ | 稳定唯一的 **Action ID**（§1） |
| 这一步会不会造成不可撤销的后果？ | **effect** 声明 + 生效当下确认（§3） |
| 它成功了吗？ | **success_evidence**，且不许只靠窗口标题（§5） |

一份档案不是脚本。脚本描述"怎么做"，档案还要描述"做的是什么、有多危险、怎么算成功、在什么范围内验证过"。

**兼容路径不是符合性声明。** `kind: external_ui_adapter` 表示这是从外部驱动别人家 GUI 的兼容层。
目标软件将来自己提供 CLI / API / 动作核心时，调用方**应当**切到原生入口，档案降级为回退方案。

---

## 1. Action ID

```
^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$      例：wechat.reply_message
```

- Action ID 是**被承诺的调用接口**。同一个 ID 在不同版本的档案里必须指向同一个业务动作。
- 不同的业务动作**不得**共用一个 ID。
- **实例 ID vs 规范 ID**：录制器只发实例 ID（效果分类 + 目标指纹，如 `wechat.reply_message.8ef87c`，
  或 `workflow.<slug>_<digest>`）。规范 ID（`wechat.reply_message`）是对外承诺的接口，
  **只能由人在提升到 `validated` 时授予**，录制器不得自封。
- ID 派生**必须**跨进程稳定。语言内置的 `hash()` 通常带每进程随机盐，不得用于派生 ID。
- 动作键与效果分类是两个概念：动作键回答"哪一个动作"，`effect.effect_id` 回答"哪一类对外影响"。

---

## 2. 生命周期与证据要求

| status | 含义 | 最低证据 |
|---|---|---|
| `draft` | 一次演示的候选，或纯手写假设 | 无。**不得**无人值守执行 |
| `learned` | 有真实示范支撑，定位器仍可能漂移 | ≥2 次**变化演示**（窗口位置、输入内容、初始状态至少各变过一次）全部通过 |
| `validated` | 在声明范围内通过回归 | 见下 |

`validated` **必须**同时满足：

1. `compatibility` 声明了 app 版本、OS build、DPI 缩放、语言范围；
2. `evidence.regression_runs` 里在该范围内有通过记录，且 `evidence.promoted_by` 记录了提升人；
3. `success_evidence` **至少有一条不是** `window.title_contains`（§5）；
4. 任何步骤**不得**依赖 `locator.fallback_absolute` 作为唯一定位手段；
5. 含 `effect` 的步骤**必须**带 `target_assertion`（§4）。

> 一次坐标录制只能产生 `draft`。声称"学会了"而拿不出上述证据的档案，应当被校验器拒收。

---

## 3. 对外效果（effect）与守卫

带 `effect` 的步骤是**对外产生不可撤销影响**的那一步：发送、发布、互动、转发、支付、删除。

规则：

- 执行器**必须**在该步生效**当下**单独确认，且**不得**把它与"是否授权本次执行"合并成一次确认。
- 确认信息**必须**包含解析出的**目标身份**（§4）。人要确认的是"发给谁"，不只是"要不要发"。
- `confirmation` 只有一个合法值：`always`。
- `reversible` 缺省按 `false` 处理。

**守卫判定不得依赖用户的措辞。** 实现**必须**至少综合三路证据：

| 证据 | 说明 |
|---|---|
| 声明意图 | 目标描述里的动词，**必须**覆盖多语言，不得只匹配单一语言的关键词表 |
| 应用族 | 最后一步落在哪个软件（进程名 > 窗口类名 > 标题）。通讯、邮件、社交、支付类软件中的终态操作**默认即对外动作** |
| 控件身份 | 被点控件的可访问性名称（"发送 / Send / 送信"…） |

任意一路命中即守卫（**fail-closed**）。判定结果**必须**带 `confidence` 与 `reasons`，使人能复核守卫判得对不对。

---

## 4. 目标断言（target_assertion）

窗口身份证据强度，由强到弱：

```
process   （进程名，基本不变）
class_name（窗口类名，随框架版本变）
title     （窗口标题，随会话和文件名变）
```

- 进程名或类名**明确对不上**的候选**必须**直接否决——那是另一个软件，不是弱匹配。
- 仅靠标题子串命中记为 `weak`。
- 对外动作的默认要求：`min_confidence: strong`、`require_unique: true`、`reconfirm_if_changed: true`。
  不满足**必须拒绝执行**，**不得**降级为"取第一个候选"。
- 人确认之后目标发生变化，**必须**重新确认。

> 为什么这条单列一节：本机实测，微信同时有 4 个窗口属于 `weixin.exe`，标题分别是
> "Weixin"×2、"图片和视频"、"微信"。标题子串匹配 + 取第一个命中，等于给"发错窗口"留了一条通路，
> 而它恰好落在风险最高的那一步上。

`expected_state_version` 与 `idempotency_key` 是**协议保留字段**，供跨设备执行使用。
当前参考实现尚未校验它们，档案里写了也不会生效——本节如实标注，避免把未实现的能力当成已有保障。

---

## 5. 成功证据（success_evidence）

支持的证据种类见 schema 的 `successEvidence.kind` 枚举，含窗口、UIA 值、文件、剪贴板、进程、浏览器地址。

- 成功**必须**由可观察证据证明，**不得**以"步骤跑完没报错"当作成功。
- `window.title_contains` 是**最弱**的一种：消息发成功和发失败，窗口标题往往完全一样。
  因此 `validated` 档案**必须**至少有一条其它种类的证据。
- 每条证据**应当**声明 `timeout_ms`。

---

## 6. 隐私

- 可打印文字**不得**写入录制产物；只保留占位符与长度。
- 涉及正文、联系人、凭据的步骤**必须**标 `log_policy: redact`。
- 截图默认关闭。

---

## 7. 版本策略

- `profile_version` 是 `"1.0"` 常量。校验器**必须**按此字段选择规则集。
- v1 只接受**向后兼容的增补**：新增可选字段、向枚举追加取值。
- 破坏性变更（删字段、改语义、收紧已有字段）走 v2，且**必须**提供 0.1→1.0 那样的迁移说明。
- 未知的额外字段：读取方**应当**保留而不是丢弃，以便不同实现间往返不丢信息。

---

## 8. 从 v0.1 迁移

| v0.1 | v1.0 | 说明 |
|---|---|---|
| `profile_version: "0.1"` | `"1.0"` | |
| 动作键可为任意字符串 | 必须匹配 Action ID 正则 | 中文目标曾塌陷成同一个 ID |
| `effect.action_id` | `effect.effect_id` | 与动作键区分开，语义不再重叠 |
| `locator.window` 只有 title/class | 增加 `process` | 只有 title 的定位器在对外动作上会被判 `weak` 而拒绝执行 |
| 无 `target_assertion` | 对外步骤必填（validated） | |
| 无 `compatibility` / `evidence` | `validated` 必填 | |

v0.1 档案仍可被读取和 dry-run，但**不得**提升到 `validated`。
