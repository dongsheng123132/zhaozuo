# 架构说明

## 总体数据流

```text
人工示范
   │
   ▼
Recorder ── 原始事件 / UIA / 截图引用 ──► recordings/
   │
   ▼
Profile Builder ── 对齐多次示范、抽取变量与稳定定位器
   │
   ▼
Shadow Profile ── 动作、输入、步骤、风险、证据
   │
   ▼
Executor ── 计划 / 定位 / 执行 / 断言 ──► 执行报告
```

## 为什么不直接保存宏

传统宏记录的是鼠标坐标和按键序列。窗口一移动、DPI 一变化或首页多一个弹窗，宏就会失效。

Shadow Profile 保存的是分层定位意图：

1. 如果软件已有可靠 CLI、协议或原生入口，直接使用；
2. 否则使用 Windows UI Automation 或无障碍树；
3. UIA 不完整时使用稳定快捷键；
4. 再退到 OCR/视觉与窗口相对位置；
5. 裸屏幕坐标只能作为有版本范围、可验证的最后兜底。

每次降级都必须进入执行报告，便于判断 Profile 是否正在变脆。

## 动作与步骤

业务动作使用稳定 Action ID，例如 `browser.open_url`。步骤只是当前软件版本下的实现细节，例如“聚焦地址栏”“输入 URL”“按 Enter”。

同一动作可以因软件版本、语言或初始状态拥有不同分支，但对调用者仍保持同一个输入输出契约。

## 与 ActionParity 的关系

正式影核的理想路径是：

```text
GUI / CLI / MCP ──► 软件自己的 Action Core
```

本项目解决的是无法修改目标软件时的兼容路径：

```text
Agent ──► Shadow Profile Runtime ──► 第三方 GUI
```

前者是架构标准，后者是外部适配。两者不能混为“目标软件已经符合影核”。当目标软件未来提供正式机器入口时，Profile 应优先切换到该入口，保留 GUI 路径做界面验证或兼容兜底。
